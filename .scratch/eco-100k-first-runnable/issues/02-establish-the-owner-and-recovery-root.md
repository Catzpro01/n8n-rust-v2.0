# 02: Establish the Owner and recovery root

**What to build:** A first-time Owner can initialize the private installation, authenticate securely, obtain an externally storable Recovery Kit, and verify that private control and public ingress have different authority.

**Blocked by:** 01: Boot the production-shaped daemon and editor shell

**Status:** resolved

- [x] First-run setup creates exactly one Owner only through the private control surface and becomes unavailable after successful initialization.
- [x] Owner passwords use calibrated Argon2id PHC storage; login, session renewal, logout, expiration, and password-hash upgrade are externally tested.
- [x] Same-origin secure session cookies, CSRF/origin validation, request limits, and sensitive-header/log redaction are enforced.
- [x] Private editor/administration routes and the Public Gateway route tree are independently policy-tested; backup, restore, update, Draft, and credential functions are never public ingress.
- [x] A root-owned/systemd-supplied master key initializes encrypted vault metadata without writing the plaintext key to SQLite, logs, configuration, Git, or browser responses.
- [x] Installer/setup creates an encrypted Owner-held Recovery Kit with checksum and one-time acknowledgement instructions.
- [x] Health clearly distinguishes Recovery Kit unacknowledged, local-recovery-only, and later Disaster-Recovery Ready states.
- [x] Wrong/missing key, session fixation, repeated login failure, CSRF, and public-route access attempts fail safely with original structured diagnostics.
- [x] Audit evidence identifies the Owner actor without persisting password, cookie, master key, or private recovery material.


## Answer

Implemented a one-time private Owner bootstrap, Argon2id PHC password policy with measured parameters and login-time hash upgrade, rotating secure sessions, CSRF/origin enforcement, bounded request bodies, persistent login limiting, and structured private-control errors. The initial Public Gateway exposes only its own liveness route; private setup, session, recovery, audit, Draft, credential, backup, restore, and update paths are not delegated into it.

A root-owned 32-byte master key is generated by the installer and delivered to the unprivileged daemon with systemd `LoadCredential`. SQLite retains only a constant-time key fingerprint and an XChaCha20-Poly1305 encrypted vault sentinel. Setup returns a one-time, Argon2id/XChaCha20-Poly1305 encrypted Owner-held Recovery Kit plus a SHA-256 checksum; only that checksum and acknowledgement time are persisted. Readiness distinguishes `setup-required`, `recovery-kit-unacknowledged`, `local-recovery-only`, and the separate future Disaster-Recovery Ready claim.
